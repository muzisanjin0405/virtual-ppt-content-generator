# 虚拟PPT内容生成器

## 1. 核心定位

本 Skill 专门用于 **假想 / 虚构 PPT 项目的完整内容生成**。

用户通常只需要输入：

- 场景
- 行业

即可生成一套能够直接进入 PPT 页面设计阶段的逐页中文文案。

核心公式：

> PPT内容 = 场景真实需求 × 行业专业知识 × 虚拟项目世界观 × 受众关注点 × 决策目标 × 页面内容形态

“真实”的含义不是资料必须来自现实企业，而是：

1. 商业逻辑真实；
2. 数据量级真实；
3. 时间线与指标自洽；
4. 行业表达真实；
5. 页面内容像真实项目，而不是泛泛的 AI 示例；
6. 内容天然适合 PPT 承载，但最终不输出任何设计说明。

## 2. 适用场景

必须兼容以下场景树，并兼容其常见别名。

### A. 商业交流
- 企业 / 产品介绍
- 招商 / 合作展示
- 营销 / 策划方案

### B. 项目汇报
- 内部汇报
  - 工作总结
  - 项目复盘
- 对外汇报
  - 客户汇报
  - 投融资 BP
  - 战略推介
- 洞察报告
  - 行业分析
  - 数据研究
  - 白皮书发布

### C. 知识变现
- 顾问方案
- 培训课件 / 课程宣讲
- 知识品牌展示

### D. 个人成长
- 求职简历
- 作品展示
- 社交名片

详细场景映射、业务问题和叙事模型见：`references/SCENE_MODELS.md`。

当用户输入的名称不完全一致时，自动映射到最接近的细分场景，不要求用户改写。

例如：

- “公司介绍” → 企业 / 产品介绍
- “渠道招商” → 招商 / 合作展示
- “年度复盘” → 内部汇报 / 工作总结或项目复盘
- “BP” → 对外汇报 / 投融资 BP
- “行业研究” → 洞察报告 / 行业分析
- “课程介绍” → 培训课件 / 课程宣讲
- “作品集” → 个人成长 / 作品展示

## 3. 触发条件

当用户提出以下需求时使用本 Skill：

- 根据“场景 + 行业”生成 PPT 内容
- 生成一套虚拟 / 假想 PPT 文案
- 为页面设计准备完整文案
- 做招商、企业介绍、营销策划、汇报、BP、行业报告、培训、作品集等 PPT 内容
- 希望内容“像真实项目”“可以杜撰数据”“不要设计说明”
- 希望先虚构一个合理项目，再生成逐页内容

如果用户只给“场景 + 行业”，直接生成，不强制追问。

## 4. 输入模型

### 4.1 最小输入

```text
场景：招商 / 合作展示
行业：茶饮
```

也支持：

```text
招商合作展示 + 茶饮
```

### 4.2 可选输入

```text
受众：区域经销商
目标：推动签约
页数：18
项目名称：可指定，也可自动生成
企业阶段：初创 / 成长 / 成熟
区域：华东 / 全国 / 海外等
内容密度：低 / 中 / 高
语言：中文 / 中英双语等
虚构强度：轻度 / 标准 / 深度
特殊要求：例如“多一些经营数据”“不要品牌故事”“偏真实商业逻辑”
```

### 4.3 缺省推断

若用户未提供：

- 受众：按场景推断；
- 目标：按场景推断；
- 项目名称：自动生成虚构名称；
- 企业阶段：按行业与场景选择最合理阶段；
- 区域：按行业与项目规模自动设定；
- 页数：按细分场景使用合理默认页数；
- 虚构强度：标准；
- 内容密度：中；
- 数据：允许生成精确模拟数据，但必须遵守自洽规则。

不需要频繁向用户确认这些默认值。

## 5. 输出目标：完整页面文案，而不是视觉大纲

最终输出必须是 **可以直接复制进 PPT 的页面内容**。

可以输出：

- 页面标题
- 副标题
- 正文
- 核心观点
- 数据
- 产品名称与规格
- 用户画像
- 案例背景、过程、成果
- 方案策略
- 时间计划
- 预算
- KPI
- 商业模式
- 招商政策
- 流程步骤
- 表格内容
- 简历经历
- 项目复盘信息
- 课程知识点

默认不要输出：

- 构图方向
- 版式建议
- 页面原型名称
- 图片建议
- 视觉载体
- 配色
- 字体
- 材质
- 摄影风格
- 动效
- 生图 Prompt
- “左图右文 / 三卡片 / 大图”等设计描述

“适合设计”通过 **内容结构与页面形态的自然变化** 体现，而不是显式写设计说明。正文长度不设统一字数上限或下限。

## 6. 先建世界，再写页面

禁止收到“场景 + 行业”后直接逐页即兴写作。

必须先在内部建立一个 **虚拟项目世界观（Project World Model）**，并将其作为整套 PPT 的唯一事实基准。

至少包含：

```text
project_identity        项目 / 企业身份
project_type            企业、品牌、产品、研究、个人、课程等
industry                 行业与细分行业
founded_or_start_time    成立 / 项目启动时间
location_scope           总部、区域、市场范围
stage                    初创 / 成长 / 成熟 / 转型 / 项目阶段
core_offer               核心产品、服务、方案或能力
customer_or_audience     核心客户 / 用户
price_or_value_band      价格带 / 项目金额 / 价值区间
channels                 渠道 / 获客 / 交付渠道
scale                    营收、客户、门店、团队、项目规模等
key_metrics              关键经营或项目指标
advantages               可被事实支撑的优势
constraints              当前问题 / 风险 / 约束
milestones               时间线与阶段成果
cases                     典型虚构案例
objective                 本次 PPT 的真实目标
next_step                 希望受众采取的下一步行动
```

这个世界观通常不需要完整展示给用户，但所有页面内容必须与它一致。

### 6.1 命名去偏与伪随机规则

当虚拟项目需要生成人物、企业、品牌、产品、课程、客户或案例名称时，必须先建立内部 **Naming Diversity Plan（命名多样性计划）**，不得直接采用模型最先联想到的名称。

#### 用户输入优先

- 用户已经指定的名称必须保留，除非用户明确要求改名；
- 用户指定的命名风格、地域、年代、语言和禁用字优先于本规则；
- 本规则约束自动生成的虚构名称，不用于擅自修改真实名称。

#### 候选池要求

1. 人物名、品牌名、产品名和案例客户名必须分别生成候选池后再选择；
2. 人物名候选不少于 12 个，至少覆盖 8 个不同姓氏，并自然混合单字名、双字名与不同语义风格；
3. 品牌 / 机构名候选不少于 10 个，至少覆盖描述型、中性专业型、姓氏 / 创始人型、隐喻型 4 类命名逻辑；
4. 产品 / 课程名优先表达对象、任务或结果，不默认堆叠“增长、赋能、进阶、领航、智学”等高频营销词；
5. 案例客户名应与主体品牌采用不同的构词方式，不能像同一套词库批量生成。

#### 禁止默认命名偏好

- 不得因为行业是教育、知识服务或个人 IP，就优先使用“知、行、学、启、智、研、思、云”等文化感或科技感高频字；
- 不得默认采用“林知X”“陈知X”“X知行”等语义化人物名，也不得把人物名写成职业主张的同义词；
- 不得让专家姓名、品牌名和方法论名称刻意共享核心字，例如“林知行—知行研究室—知行方法”；
- 不得连续依赖“研究室、实验室、研习社、研究院、学院、智库”等后缀。只有当组织形态确实匹配时才可使用，并应与其他候选结构比较后选择；
- 不得把当前行业关键词直接嵌入所有名称。职业教育项目可以有行业描述，但人物、品牌、产品与案例不应全部重复“职教、职业、岗位、课程”等词；
- 不能通过建立另一组固定名字来替代旧偏好。示例中的任何姓名和品牌都不得成为默认答案。

#### 受控伪随机选择

1. 以本次用户输入中稳定存在的字段形成内部种子：`场景 + 行业 + 页数 + 受众 + 目标 + 用户关键词`；
2. 对候选池完成禁用字、语义撞名、现实机构重名风险和跨名称重复检查后，再按种子映射选择，不得总取首个候选；
3. 不同命名槽位使用不同偏移量；若产生重字、同音、同义或结构雷同，则按候选池顺序循环后移，直到通过检查；
4. 同一份 PPT 内名称必须保持稳定；在用户输入或项目设定发生变化时，应重新计算选择，不沿用上一份内容的习惯性命名；
5. 伪随机只负责打散偏好，最终选择仍须服从行业、地域、人物年龄、组织属性与叙事真实性。

#### 命名审计

生成世界观后必须检查：

- 人物姓名是否与品牌、课程或方法论形成无理由的语义呼应；
- 多个虚拟名称是否反复使用相同汉字、后缀或节奏；
- 名称是否过度文艺、过度科技化，或明显像为主题临时拼出的代号；
- 名称是否与现实知名企业、机构、专家或品牌高度近似；
- 删除行业说明后，名称是否仍像自然存在的人名或组织名。

任一检查不通过时，必须回到对应候选池重新选择，不得只通过改一个字规避。

## 7. 场景先决定“真实业务问题”

场景不是一套固定页标题，而是一组这份 PPT **必须回答的问题**。

示例：招商 / 合作展示必须回答：

1. 为什么现在值得进入？
2. 这个品牌 / 项目到底卖什么？
3. 谁会买？
4. 为什么能卖？
5. 已经验证到什么程度？
6. 合作伙伴怎么获得收益？
7. 投入与门槛是什么？
8. 总部 / 项目方提供什么？
9. 风险如何降低？
10. 下一步怎么合作？

企业 / 产品介绍、营销方案、复盘、BP、白皮书、培训等必须使用各自的业务问题，不允许换几个标题后复用同一套逻辑。

详见 `references/SCENE_MODELS.md`。

## 8. 行业决定“专业内容是什么”

行业不是固定 PPT 模板，而是 **专业内容知识包**。

基础行业族：

1. 消费与零售
2. 科技与互联网
3. 金融与专业服务
4. 医疗健康
5. 地产与文旅
6. 制造与产业
7. 教育与知识服务
8. 公共与文化
9. 可扩展自定义行业

细分行业例如：

- 茶饮、咖啡、美妆、服饰
- AI、SaaS、智能硬件
- 投资、咨询、保险
- 医药、医疗器械、健康管理
- 房地产、酒店、旅游
- 汽车、新能源、制造、物流
- 教培、课程、出版
- 政务、城市宣传、文化机构

每个行业都应调用其自然存在的业务字段、专业术语、指标、单位与流程。

详见 `references/INDUSTRY_MODULES.md`。

## 9. 虚构数据规则

### 9.1 允许虚构

在“虚拟 / 假想 PPT”模式中，允许生成：

- 企业名称
- 品牌名称
- 产品名称
- SKU
- 价格
- 营收 / GMV
- 增长率
- 客户数量
- 门店数量
- 转化率
- 复购率
- 毛利率
- 项目预算
- 时间周期
- 渠道结构
- 用户调研结果
- 案例成果
- 团队人数
- 市场覆盖
- 虚拟客户与合作伙伴

但这些数据必须是 **模拟事实**，不是随机数字。

### 9.2 默认披露方式

在整套输出前，用一句话说明：

> 以下企业、人物、案例与经营数据均为虚构示例，仅用于 PPT 内容与页面设计。

不需要在每一个数字旁反复写“模拟数据”，避免破坏页面文案的真实感。

### 9.3 禁止伪造现实事实

除非用户明确提供或指定为概念提案，不要虚构：

- 与真实知名企业的合作关系
- 真实奖项
- 真实专利
- 真实官方认证
- 真实政府背书
- 真实医院 / 高校 / 金融机构合作
- 对现实上市公司的虚假经营数据

虚拟项目应优先搭配虚拟客户、虚拟渠道、虚拟机构名称。

### 9.4 数据必须自洽

生成后内部检查：

- 同比增长计算正确；
- 各渠道占比合计约等于 100%；
- 营收与客户 / 门店规模处于合理量级；
- 单价 × 销量与 GMV 不发生明显冲突；
- 毛利率与渠道折扣逻辑一致；
- 项目预算各项加总正确；
- 项目进度与启动时间一致；
- “成立 2 年”不能出现“5 年累计”；
- 产能、团队、客户量不能明显超出企业阶段；
- 前后页面同一指标不得变化。

完整规则见 `references/REALISM_RULES.md`。

## 10. 页面标题、项数与内容形态规则

“完整文案”不等于“每页写一篇文章”。内容必须完整，但要天然适合页面承载。

### 10.1 主标题长度：统一 8–16 字

除用户明确指定不可改写的固定标题、品牌名、作品名或专有项目名外，**所有页面主标题默认控制在 8–16 个中文视觉字符**。

规则：

- 优先写 8–14 字，最多 16 字；
- 不要把“背景 + 判断 + 结果”全部塞进一个标题；
- 标题需要承载页面结论，但只表达一个核心判断；
- 更完整的解释移入副标题、正文、数据或要点；
- 避免连续使用逗号、冒号、破折号拼成长句；
- 数字、英文缩写和品牌名可按一个语义词组理解，不为凑字数机械扩写；
- 若用户给出固定标题，则保留用户原文，不强制压缩。

弱例：

- 年轻消费者没有离开茶，只是不再接受复杂的饮茶方式

优化：

- 年轻人的饮茶方式正在改变

弱例：

- 我们已经完成第一阶段验证：增长主要来自复购，而不是持续铺新点位

优化：

- 增长正在从铺货转向复购

### 10.2 “项数”的定义

“项数”是指一页中**并列、可独立阅读的主要信息单元数量**，例如：

- 3 个客群 = 3 项；
- 4 个核心数据 = 4 项；
- 5 个流程步骤 = 5 项；
- 1 个完整结论 + 一段解释 = 1 项；
- 表格中的 4 个产品行可视为 4 项；
- 标题、副标题、结论说明不单独计项。

### 10.3 允许 1 项页面

**项数允许为 1。** 当页面的真实任务只是强化一个核心判断、一个产品、一个案例结论、一个核心数字或一个行动主张时，应保留为 1 项，不要为了形式完整强行拆成 2 项。

适合 1 项的页面包括：

- 单一核心观点；
- 单一产品聚焦；
- 单一关键结论；
- 单一大型案例结果；
- 单一核心目标；
- 收尾行动主张。

### 10.4 2 项页面必须有明确语义理由

2 项不是默认结构。只有内容本身天然是“双向关系”时才优先使用，例如：

- A / B 对比；
- 现状 / 目标；
- 问题 / 解法；
- 两类核心业务；
- 双轨合作模式。

如果两个信息本质上属于同一个观点，应合并成 1 项；如果两项内部都包含多个独立维度，应拆成 3–5 项。

禁止为了“看起来像一页 PPT”习惯性生成两个并列模块。

### 10.5 全套页面项数必须做分布平衡

在逐页写作前，必须先创建一份内部 **Item Count Plan（项数计划）**。

对 12 页及以上的 PPT，在业务合理的前提下：

- 1 项、3 项、4 项、5 项页面都应有自然出现；
- 2 项页面原则上不超过全部内容页的 15%–20%；
- 任意单一项数不应长期占据整套 PPT 的主导，通常不超过约 30%；
- 3 项和 4 项可作为最常见结构，但两者也不要单独垄断；
- 5 项及以上用于信息天然丰富的产品矩阵、数据、能力、渠道、策略等页面；
- 6 项以上只在业务确有必要时使用，避免纯粹为平衡数字而扩项。

对常见 16–20 页 PPT，可参考以下软性分布，而不是硬配额：

- 1 项：2–4 页；
- 2 项：1–3 页；
- 3 项：3–5 页；
- 4 项：3–5 页；
- 5 项：2–4 页；
- 6 项以上：0–2 页。

**业务合理性优先于数学平均。** 如果某类页面天然需要固定项数，应服从内容本身，不得为了均衡强行增删。

### 10.6 不同内容类型的合理项数

- 封面：1 个主命题；
- 观点 / 章节页：1 项为主，也可 3 项辅助；
- 普通内容页：1、3、4、5 项均可，避免默认 2 项；
- 数据页：3–5 个核心数据；
- 客群页：3–4 类人群为主；
- 产品 / 服务矩阵：3–6 项；
- 案例页：可用 1 个完整案例，也可拆为 3–4 个阶段信息；
- 策略页：3–5 个策略支柱；
- 流程页：**不得为 1 项或 2 项**，默认 4–7 步；若真实流程确实很短，最低也应是 3 步；
- 时间线 / 路线图：3–6 个阶段；
- 竞品对比：2 项只适用于真正的 A/B 对比，更多对象则按真实数量输出；
- 政策 / 能力 / 渠道：3–6 项；
- 收尾页：1 个行动主张，可附联系信息，不为凑数拆项。

### 10.7 正文不设固定字数约束

**删除所有针对正文、段落、单项说明、流程步骤、策略说明、案例说明的固定字数上下限。**

生成时不得因为预设字数而机械缩短或扩写内容。正文长度由以下因素共同决定：

- 场景的真实表达习惯；
- 当前页面承担的业务任务；
- 信息是否已经完整；
- 页面在整套叙事中的节奏；
- 内容本身更适合叙述、列表、数据、表格还是留白展示。

允许出现：

- 只有标题、没有正文的页面；
- 标题 + 一段完整长文本的页面；
- 标题 + 一句短说明的页面；
- 标题 + 1 个完整信息单元；
- 标题 + 多个并列信息单元；
- 标题 + 数据 / 表格 / 流程 /案例等结构。

禁止为了“控制字数”把本应完整的一段叙述拆成多个 bullet，也禁止为了显得内容丰富而给本应留白的页面强行补正文。

### 10.8 页面内容形态采用受控伪随机

在逐页写作前，除 Item Count Plan 外，还要创建内部 **Content Form Plan（内容形态计划）**。

它不是纯随机，而是 **场景约束下的伪随机分配**：同一场景、行业、页数下保持叙事合理，同时让页面文案形态自然变化，避免所有页面都长成“标题 + 正文 + 3条要点”。

可选内容形态包括：

1. **Title Only**：只有标题，可附项目名 / 日期等必要文字；正文为空。
2. **Narrative Longform**：标题 + 一段完整长文本，不拆条目。
3. **Narrative Short**：标题 + 一段简短说明。
4. **Single Focus**：标题 + 1 个完整信息单元。
5. **Parallel Points**：标题 + 3–6 个并列项；2 项仅在天然二元关系时使用。
6. **Data Facts**：标题 + 若干关键数字 / 指标及必要说明。
7. **Table / Matrix**：标题 + 适合比较、规格、政策、预算等的表格内容。
8. **Case Narrative**：标题 + 一个完整案例叙述，或按真实阶段拆解。
9. **Process / Timeline**：标题 + 3 个以上真实步骤 / 阶段。
10. **Quote / Claim**：标题 + 一句关键主张、引语或结论，可无额外正文。

伪随机规则：

- 先根据场景筛选“允许出现”的内容形态，再进行变化；
- 同一种内容形态原则上避免连续出现 3 页以上；
- 不能为了变化破坏业务逻辑，例如真实流程仍必须是流程；
- 标题页、展示页、章节页等可自然形成 0 项文字页面，不计入普通内容页的项数均衡；
- 长文本页属于 1 个叙述单元，不因项数均衡而强拆；
- 2 项页面仍只保留给真正的二元关系；
- 当页面信息天然丰富时，可以出现 4–6 项甚至更多，但不得为凑项数虚构低价值信息。

### 10.9 特殊页面必须被允许自然出现

#### 企业 / 产品介绍

企业介绍、品牌介绍、机构介绍等场景中，允许并鼓励在合适位置自然出现 **“标题 + 一段完整长文本”** 的叙述页，例如：

- 企业概述；
- 品牌缘起；
- 核心主张；
- 当前阶段说明；
- 创始背景或战略转折。

这类页面只有 1 个叙述单元，不应为了项数均衡强拆成 3–4 条。

#### 作品展示 / Portfolio

作品集允许并应自然出现 **“只有标题文字，其余内容由作品图像承担”** 的展示页。

这类页面：

- 可以只有作品名 / 项目名作为标题；
- 可以没有正文、要点、说明文字；
- 文本项数视为 0；
- 不需要为了“完整文案”补设计理念或项目说明；
- 但一个完整项目仍应在前后其他页面中提供必要的背景、任务、决策与结果，不能整套作品集只剩标题页。

同理，摄影、建筑、空间、品牌视觉、UI、插画等以作品本身为主要信息的场景，都可以使用这种标题-only 页面。

#### 章节 / 过渡 / 收尾

章节页和收尾页允许采用标题-only、标题 + 一句主张、标题 + 一段文字等简洁形态。章节页必须与目录条目一一对应；收尾页必须是整套大纲的最后一页，并包含与本次主题相关的结尾语。

详细内容形态与场景权重见 `references/CONTENT_VARIATION.md`。

### 10.10 所有大纲必须包含目录页与章节页

无论应用场景、总页数或阅读方式如何，最终大纲都必须包含 **1 页目录页**，并同时包含与目录条目一一对应的章节页。用户没有主动要求目录时也不得省略。

必须遵守：

- 封面之后安排目录页；若有必要的前言或开场说明，目录页仍须位于第一个章节页之前；
- 目录中的章节名称、数量和顺序必须与后续章节页完全一致；
- 每个目录条目都必须有对应章节页，每个章节页也必须出现在目录中；
- 每个章节页之后必须有属于该章节的实质内容，不能用空章节凑页数；
- 目录页计入用户指定的总页数；全部章节页均作为额外插入页，**不计入用户指定的总页数**，也不得挤占正文页额度；
- 最终实际输出页数 = 用户指定页数（或场景默认页数）+ 章节页数量；例如用户要求 18 页、目录含 4 个章节时，最终输出 22 页；
- 短篇内容也不能取消目录和章节页，应压缩章节数量与正文层级；必要时只设 1 个一级章节；
- 禁止任何“无需目录”“省略目录”“仅连续叙事”的例外。

在分配页面前，必须建立内部 **Agenda-Section Pair Plan**，先锁定目录页、章节名称、章节页位置和各章内容范围。

### 10.11 最后一页必须是主题结尾页

每套大纲的最后一页必须是独立的结尾页，且已经计入用户指定的总页数。

结尾页必须：

- 位于全部正文、案例、计划、附录和联系方式之后；其后不得再有任何页面；
- 包含一句与本次主题、核心价值、受众决策或下一步行动直接相关的结尾语；
- 回扣整套内容的主命题，并与场景语气一致：商业提案可强调合作与行动，汇报可强调下一阶段，培训可强调实践，作品集可强调专业主张；
- 结尾语应具体、自然、可直接放入 PPT，不得只写“谢谢观看”“感谢聆听”“THANKS”或其他与主题无关的通用致谢；
- 可以附必要的联系信息或行动入口，但不能用联系信息替代主题结尾语。

若用户提供固定结尾语，优先保留；但若它与主题明显无关，应在不改变原意的前提下补充主题相关表达。

## 11. 文案真实性规则

### 11.1 观点必须由事实支撑

避免：

- 行业领先
- 强势破局
- 全方位赋能
- 深度布局
- 极致体验
- 赋能增长
- 匠心打造
- 生态闭环
- 携手共赢
- 国内顶尖

除非后面有具体事实证明。

优先写：

- “常规 SKU 保持 28 天安全库存，华东仓订单可在 24 小时内出库。”

而不是：

- “强大的供应链为合作伙伴保驾护航。”

### 11.2 标题应承载结论，同时保持 8–16 字

弱标题：

- 市场分析
- 产品介绍
- 用户画像
- 核心优势
- 营销策略

更好的标题：

- 年轻人的饮茶方式正在改变
- 核心产品覆盖四类消费场景
- 增长正在从铺货转向复购
- 首次体验后的转化仍是短板

允许保留必要的传统标题，但优先使用短而有信息量的结论型标题。超过 16 字时，优先把解释性内容移到正文。

### 11.3 不要所有页面都使用同一种句式

整套内容中应自然混合：

- 观点型标题
- 数据型标题
- 问题型标题
- 结论型标题
- 行动型标题
- 名称型标题（产品、项目、课程等必要场景）

## 13. 内部生成算法

必须按以下顺序执行。

### Step 1 — 解析场景

识别一级场景、二级场景，以及可能的三级场景。

例如：

```text
项目汇报 / 对外汇报 / 投融资 BP
```

### Step 2 — 识别行业

识别一级行业 + 细分行业。

例如：

```text
科技与互联网 / 企业服务 / AI SaaS
```

### Step 3 — 推断受众与决策目标

如果用户没有提供，则根据场景自动推断。

### Step 4 — 建立真实业务问题

从 `SCENE_MODELS.md` 中加载该场景必须回答的问题。

### Step 5 — 加载行业知识包

从 `INDUSTRY_MODULES.md` 中选取与当前业务问题相关的专业字段。

不要一次性倾倒所有行业模块。

### Step 5.5 — 创建命名多样性计划

在建立虚拟项目世界观之前，按照 6.1 的规则分别创建人物、品牌 / 机构、产品 / 课程与案例客户候选池，完成去偏过滤和受控伪随机选择。用户指定名称直接锁定，不进入自动改名流程。

### Step 6 — 创建虚拟项目世界观

生成企业 / 项目 / 个人 / 课程的基础事实，并建立统一事实表。

### Step 7 — 创建数据账本

为需要使用的数据预先确定：

- 指标名
- 指标值
- 时间范围
- 单位
- 相关指标
- 适用页面

后续不得随意改动。

### Step 8 — 建立叙事顺序

按场景的真实决策逻辑安排内容，而不是按“品牌故事 → 产品 → 结束”的万能模板。

### Step 8.5 — 建立目录与章节配对计划

所有场景都必须建立 Agenda-Section Pair Plan：

- 固定安排 1 页目录页；
- 根据叙事顺序确定一级章节；
- 为每个目录条目安排 1 页对应章节页；
- 确保章节名称、数量和顺序完全一致；
- 将章节页标记为额外插入页，不纳入用户指定或默认的总页数；
- 短篇内容通过减少章节数量适配，不得取消目录页或章节页。

本计划必须在分配总页数前完成。

### Step 9 — 分配页数

先在用户指定或默认的总页数内锁定封面、目录页和最后一页结尾页，再分配各章内容页；随后在对应章节开始前额外插入章节页。章节页不消耗总页数额度，最终实际输出页数必须等于“计数页数 + 章节页数量”。每一页只承担一个主要任务。

### Step 9.4 — 规划全套内容形态

在确定每页项数之前，先根据场景、行业与页面任务生成 **Content Form Plan**：

- 哪些页是完整叙述；
- 哪些页只需要一句主张；
- 哪些页需要并列项；
- 哪些页是数据 / 表格 / 流程；
- 哪些页允许只有标题而没有正文。

采用受控伪随机，让整套页面的文字形态有真实项目中的节奏变化。不得先固定“每页都要有正文和要点”，再往里填内容。

### Step 9.5 — 规划全套项数分布

在 Content Form Plan 基础上，再为需要并列信息的页面确定合理项数，并检查全套分布：

1. 先锁定语义上有硬约束的页面，例如流程至少 3 项、数据按真实指标数量、真正 A/B 对比 2 项；标题-only / 纯展示页可为 0 项，并从普通项数均衡中排除；
2. 再为可自由组织的页面分配 1、3、4、5 项，避免连续大量出现 2 项；
3. 如果出现过多 2 项页：
   - 两项本质同属一个观点 → 合并为 1 项；
   - 两项内部各含多个独立维度 → 拆为 3–5 项；
   - 只有真正双向关系才保留 2 项；
4. 检查是否出现流程 / 时间线只有 1–2 项，若有必须重构；
5. 最终以业务合理性为准，不为了平均而制造虚假信息。

### Step 10 — 选择内部内容类型

内部可使用：

```text
cover
agenda
section
showcase
narrative
statement
context
market
problem
audience
company
product
product_matrix
service
comparison
data
case
process
strategy
business_model
policy
budget
kpi
roadmap
timeline
review
lesson
resume
portfolio
closing
```

这些类型用于控制写作结构，默认不要在最终结果中输出类型名称。

### Step 11 — 写完整页面内容

为每页生成实际可使用文字。目录页必须列出全部一级章节；章节页必须逐一出现；最后一页必须写成包含主题相关结尾语的结尾页。

### Step 12 — 做一致性检查

检查事实、数据、时间、角色、产品、命名多样性、页面重复度与页数口径。分别核对计数页数和章节页数量，确认最终实际输出页数 = 计数页数 + 章节页数量。

### Step 13 — 做“页面可用性检查”

确保：

- 不把所有页面机械处理成相同文字结构；
- 允许必要的长文本叙述页，也允许正文为空的标题-only 展示页；
- 页面内容形态与场景、页面任务一致；
- 一页只回答一个主要问题；
- 主标题通常为 8–16 字；
- 允许 1 项页面，不强制补成 2 项；
- 2 项页面没有在全套中异常集中；
- 1 / 3 / 4 / 5 项页面按语义自然分布；
- 流程、时间线等结构没有出现 1 项或 2 项的伪流程；
- 不输出视觉设计说明；
- 若页面只有标题或一句话，这是由展示 / 章节 / 主张等真实页面任务决定，而不是内容缺失；
- 目录页已输出，且每个目录条目都有对应章节页；
- 所有章节页均未占用用户指定或默认的总页数，最终实际输出页数已正确增加；
- 最后一页是主题结尾页，其后没有附录、联系方式或其他页面；
- 结尾语明确呼应本次主题，而不是通用致谢；
- 整套信息足够完整，可直接用于假想页面设计。

### Step 14 — 做最终大纲完整性审计

把封面、目录页、全部章节页、内容页和结尾页作为一套完整大纲重新审查，而不是只检查单页：

1. **真实性**：项目身份、规模、案例、机构关系、行业细节是否可信，是否存在无依据的背书、奖项、认证、专利或绝对化结论；
2. **逻辑性**：受众与目标是否一致，章节顺序是否形成因果或决策推进，结论是否有前文事实支撑，前后是否互相矛盾；
3. **数据正确性**：重新核算增长率、占比、预算、单价 × 数量、单位经济和时间跨度，核对单位、口径、年份与数据账本；
4. **完整性**：场景必须回答的业务问题是否都有落点，是否存在关键缺页、重复页、孤立页或低价值凑页；
5. **结构配对**：确认必需的目录页已经存在，目录条目与章节页的名称、数量、顺序一一对应，每章都有实质内容；
6. **页数口径**：确认目录页计入总页数、章节页全部不计入总页数，且实际输出页数等于计数页数加章节页数量；
7. **结尾检查**：确认最后一页是结尾页，结尾语与主题直接相关，其后不存在任何页面。
8. **命名去偏**：确认人物、品牌、产品、方法论和案例名称来自分离候选池，没有主题字强行呼应、高频字聚集、后缀批量复用或固定姓名偏好。

发现任何不真实、逻辑错误、数据错误或结构冲突时，必须回到世界观、数据账本或页面大纲修正，并重新执行本审计；不得带着已知问题输出。详细核验见 `references/REALISM_RULES.md`。

---

## 14. 默认输出格式

### 14.1 开头说明

仅用一句：

> 以下企业、人物、案例与经营数据均为虚构示例，仅用于 PPT 内容与页面设计。

### 14.2 可选的“项目设定”

默认简要输出 5–8 行，用于让用户快速理解虚拟背景：

```text
项目：
场景：
行业：
受众：
目标：
项目阶段：
页数（不含章节页）：
章节页：X 页（额外输出，不计入上述页数）
实际输出页数：
```

如果用户明确说“只要逐页文案”，则不输出项目设定。

### 14.3 逐页完整文案

每页根据真实页面任务选择字段，**不强制每页有正文，也不强制每页完全同构**。标题-only、长文本叙述、数据、表格、流程、案例等都属于有效输出。

基础形式：

```text
P01
标题：
副标题：
辅助信息：

P02
标题：
正文：
核心信息：
- ...
- ...
- ...

P03
标题：
核心数据：
- 4,860万元｜2025年度全渠道GMV
- 286家｜稳定合作零售终端
- 31.7%｜核心产品年度复购率
结论：
...
```

允许自然输出表格、流程、案例、预算、KPI 等内容结构。

也允许：

```text
P05
标题：关于澄野科技
正文：
澄野科技成立于2021年……（根据企业真实叙事需要形成一段完整长文本，不强拆条目）
```

以及作品集中的：

```text
P09
标题：NOVA 城市夜跑视觉系统
```

此时不补正文、不补要点；页面的其他信息由作品视觉承担。

### 14.4 结尾

逐页文案的最后一页必须按以下结构输出：

```text
PXX
标题：根据场景拟定的结尾标题
结尾语：与本次主题、核心价值或下一步行动直接相关的一句话
联系信息：（仅在需要时输出）
```

结尾语必须根据具体项目重新创作，不得只用“谢谢观看”“感谢聆听”“THANKS”等通用致谢。结尾页之后不再输出任何逐页内容，也不额外输出“视觉建议”“版式建议”“下一步生图 Prompt”。

## 15. 场景适配要求

### 商业交流
内容要能够支持商业说服与下一步行动，不要只讲品牌故事。

### 项目汇报
内容必须有目标、事实、结果、问题、判断、下一步，避免写成宣传稿。

### 知识变现
内容必须体现方法、知识结构、能力证明与转化路径，避免只做个人简介。

### 个人成长
内容要围绕个人能力、经历、作品与岗位 / 合作价值展开，虚构内容时必须保持人物经历、年份与能力成长一致。

详细规则见 `references/SCENE_MODELS.md`。

## 16. 特殊模式

### 16.1 深度虚构模式

适合用户说：

- “做得像真实项目”
- “数据可以编”
- “需要很完整”
- “我要拿来做作品集 / 假想设计”

增加：

- 具体品牌 / 公司背景
- 产品命名
- 价格与规格
- 渠道与区域
- 经营数据
- 虚构客户案例
- 项目时间线
- 预算 / KPI / 政策（若场景需要）

### 16.2 轻度虚构模式

适合用户只想快速出稿。

减少次要背景，只保留页面需要的事实。

### 16.3 用户给定资料模式

如果用户提供现有企业资料或已有大纲：

- 保留用户提供的确定事实；
- 仅对空白区域补充虚构内容；
- 不 silently 改写用户给出的关键数字；
- 如果真实资料与虚构内容混用，在开头说明哪些为用户资料、哪些为补充模拟内容。

## 17. 质量验收

输出前必须内部确认：

```text
✓ 已识别到具体细分场景
✓ 已识别行业与专业字段
✓ 已建立统一虚拟项目世界观
✓ 已建立命名多样性计划，并完成候选池去偏与伪随机选择
✓ 已建立并校验数据账本
✓ 内容符合目标受众的真实关注点
✓ 页面之间存在清晰叙事推进
✓ 每页只承担一个主要任务
✓ 已输出目录页，目录条目与全部章节页的名称、数量、顺序逐一对应
✓ 即使是短篇场景，也没有省略目录页或章节页
✓ 章节页均作为额外插入页，没有占用用户指定或默认的总页数
✓ 最终实际输出页数 = 计数页数 + 章节页数量
✓ 最后一页是主题结尾页，且其后没有任何页面
✓ 结尾页包含与主题、价值或下一步行动相关的结尾语，而非通用致谢
✓ 已使用场景约束下的内容形态伪随机，而非统一模板
✓ 长文本页没有被强拆，标题-only展示页没有被强行补正文
✓ 完整文案可直接用于PPT页面设计
✓ 没有输出构图、版式、配色或图片建议
✓ 没有随意嫁接真实知名企业合作关系
✓ 人物、品牌、产品与案例名称没有主题字强行呼应或高频命名偏好
✓ 没有前后冲突的数据与时间线
✓ 已对整套大纲完成真实性、逻辑性、数据正确性与内容完整性审计
✓ 审计发现的问题已修正并复检，而不是保留在最终输出中
✓ 没有过量“赋能、领先、闭环、共赢”等空泛话术
```

## 19. 禁止事项

- 不要把“完整文案”理解为“每页都必须有固定长度正文”；需要长文时可以长，需要留白时可以没有正文。
- 不要输出视觉大纲。
- 不要输出设计 Brief。
- 不要输出布局 / 构图 / 色彩 / 字体 / 图片建议。
- 不要只输出目录级标题。
- 不要省略目录页或任何与目录条目对应的章节页。
- 不要把章节页计入用户指定或场景默认的总页数，也不要用章节页替换正文页。
- 不要把附录、联系信息、补充说明或其他页面放在结尾页之后。
- 不要用“谢谢观看”“感谢聆听”“THANKS”等通用致谢代替主题结尾语。
- 不要对所有场景复用招商或品牌介绍逻辑。
- 不要生成前后矛盾的数字。
- 不要无缘由加入真实知名公司作为客户。
- 不要用空泛营销词替代业务事实。
- 不要每页都写成“三条卖点 + 一段正文”的机械模板。
- 不要设置或暗中遵循任何统一的正文、段落、单项说明字数上下限。
- 不要为了凑页数拆分无价值页面。
- 除非用户明确要求，否则不要生成 PPT 文件本身。
